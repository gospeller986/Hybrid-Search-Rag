# Hybrid Search RAG

A local-first Retrieval-Augmented Generation system over the WHO *Guideline for the
Pharmacological Treatment of Hypertension in Adults* (2021), combining dense
(embedding) search and sparse (BM25) keyword search via Reciprocal Rank Fusion,
with answers generated by a local LLM through Ollama.

Built as a learning project — this README documents not just what the system does,
but *why* each piece was built the way it was, including the dead ends and bugs
found along the way.

## Quick start

**Prerequisites**: Python 3.12, [`uv`](https://docs.astral.sh/uv/), and
[Ollama](https://ollama.com) installed locally.

```bash
# 1. Install dependencies
uv sync

# 2. Configure environment
cp .env.example .env   # defaults are fine for local use

# 3. Pull the local model (matches OLLAMA_MODEL in .env)
ollama pull medgemma:4b

# 4. Ingest the sample document (already indexed if data/processed/chroma exists)
uv run uvicorn hybrid_search_rag.api.main:app --host 127.0.0.1 --port 8000 &
curl -X POST http://127.0.0.1:8000/ingest -H "Content-Type: application/json" \
  -d '{"filename": "who_hypertension_guideline_2021.pdf"}'

# 5. Start the frontend, in a second terminal
uv run streamlit run frontend/app.py
```

Open the Streamlit URL it prints (default `http://localhost:8501`) and ask a
question. See [Running it](#running-it) and [API reference](#api-reference)
below for more detail, and [Design decisions](#design-decisions-in-the-order-they-were-made)
for the reasoning behind how it's built.

## Why hybrid search

Dense (embedding) search is good at matching meaning — it finds "myocardial
infarction" when you search "heart attack." Sparse (BM25) search is good at
matching exact terms — it finds the chunk containing "140 mmHg" when you search
for that exact threshold, which embeddings can blur. Combining both, rather than
picking one, was the entire premise of this project. See [Fusion](#4-fusion-rrf_k--60)
below for a concrete example of why this matters, not just in theory.

## Stack

| Layer | Choice | 
|---|---|
| Language / env | Python 3.12, managed with `uv` |
| Backend | FastAPI + Uvicorn |
| Frontend | Streamlit |
| PDF extraction | `pymupdf` |
| Chunking | LangChain `RecursiveCharacterTextSplitter` (token-aware) |
| Embeddings | `sentence-transformers`, `all-MiniLM-L6-v2` (local, no API key) |
| Vector store | ChromaDB (persistent, embedded) |
| Keyword search | `rank-bm25` (BM25Okapi) |
| Fusion | Reciprocal Rank Fusion (hand-implemented) |
| LLM | `medgemma:4b` via Ollama (local, no API key) |

Everything runs locally — no external API keys, no cloud services. This was a
deliberate constraint, not a limitation we ran into.

## Architecture

```
src/hybrid_search_rag/
├── config.py              — centralized settings (pydantic-settings, reads .env)
├── ingestion/
│   ├── loaders.py         — PDF → per-page text (pymupdf, running-header stripping)
│   ├── chunking.py        — text → token-bounded, page-tracked chunks
│   └── pipeline.py        — orchestrates load → chunk → embed → store
├── retrieval/
│   ├── dense.py           — embeddings + Chroma similarity search
│   ├── sparse.py          — BM25 keyword search
│   └── fusion.py          — Reciprocal Rank Fusion of the two
├── generation/
│   └── llm.py             — prompt construction, relevance gating, Ollama calls
├── storage/
│   ├── vector_store.py    — Chroma persistent client (documents + metadata + vectors)
│   └── keyword_index.py   — in-memory BM25 index, rebuilt from Chroma on demand
└── api/
    ├── main.py             — FastAPI app
    ├── schemas.py          — request/response models
    └── routes/
        ├── search.py       — POST /search, POST /search/stream
        └── ingest.py       — POST /ingest
frontend/
└── app.py                  — Streamlit chat UI, consumes the streaming endpoint
data/
├── raw/                     — source PDFs
└── processed/chroma/        — Chroma's persisted SQLite + HNSW index files
```

The `retrieval/` ↔ `storage/` split is deliberate: `storage/` only knows how to
read/write a particular backend (Chroma, BM25); `retrieval/` owns search logic
and exposes a symmetric interface (`dense.search()`, `sparse.search()`) that
`fusion.py` can combine without caring how either one is implemented underneath.

## Design decisions, in the order they were made

### 1. `src/` layout + Hatchling build backend

The package lives at `src/hybrid_search_rag/`, not flat at the repo root. This
is deliberate: a flat layout lets Python accidentally import your package from
the working directory even when it isn't properly installed, which can mask
packaging bugs that only surface later (e.g. in CI or a fresh clone). The
`src/` layout forces the package to be installed (`uv sync`, editable install)
before it's importable, which is what we want.

`pyproject.toml` declares `hatchling` as the build backend with
`packages = ["src/hybrid_search_rag"]`, so `uv sync` installs the project's own
code as an editable package — anywhere in the codebase, `from hybrid_search_rag.x
import y` resolves correctly.

### 2. PDF extraction: `pymupdf` over `pypdf`

We started with `pypdf` (simpler, BSD-licensed). Testing it against the real
WHO PDF surfaced a real bug: certain ligature/kerning pairs extracted with a
spurious inserted space — `"Cardiovascular"` came out as `"Car diovascular"`,
`"recommendations"` as `"r ecommendations"`, etc. This isn't cosmetic:

- **BM25 relies on exact token matching** — a query containing "cardiovascular"
  cannot match an indexed chunk containing the broken tokens "car" and
  "diovascular" separately.
- **Embeddings encode a subtly wrong signal** for any chunk containing broken
  words.

We measured this concretely: `pypdf` produced ~3,600 suspicious split-word
patterns in the corpus; switching to `pymupdf` produced **zero** — confirmed
by checking that known-good words (`"Cardiovascular"`, `"recommendations"`,
etc.) were fully intact and their broken variants were completely absent.
`pymupdf` is AGPL-licensed rather than BSD, which matters for commercial
redistribution but not for this project.

`loaders.py` also strips a repeating running header (the document title,
which repeated as the first line on ~44% of pages) using a generic heuristic
— count each page's first line, and treat one that repeats across many pages
as boilerplate — rather than hardcoding the exact string, so it generalizes
to documents with a different header.

### 3. Chunking: LangChain `RecursiveCharacterTextSplitter`, token-aware

**What we tried first:** a hand-rolled, structure-aware chunker that split on
the document's numbered section headers (`3.1 Blood pressure threshold...`),
merging short sections and sub-splitting long ones. This required real
engineering to get right — filtering out Table-of-Contents false positives
(headers appear there too, followed by a page number on the next line), and a
hierarchical fallback (sentence → line → hard token-slice) for the one
section that had almost no punctuation (a contributor list table), which
otherwise produced a single unsplittable 1,896-token chunk.

**Why we abandoned it:** once built, we measured the actual section-size
distribution and found the "structure-aware" benefit was mostly theoretical —
18 of 33 detected sections already exceeded our token ceiling, some by 50x
(one section, effectively "everything after the last detected heading,"
was ~13,856 tokens). Most chunks were going to come from the fallback
sub-splitter regardless of the header-based framing, and the header
detection itself introduced real bugs (ToC filtering, mislabeling later
back-matter/annex content with an earlier section's title). The complexity
wasn't paying for itself.

**What we replaced it with:** LangChain's `RecursiveCharacterTextSplitter`,
via `.from_huggingface_tokenizer()` — this measures chunk size in *real
tokens from our own embedding model's tokenizer*, not characters, and
cascades through separators (paragraph → sentence → line → character) until
every piece fits. This is the same algorithmic idea as our hand-rolled
version, but battle-tested, far less code, and — measured on the same
document — produced a *tighter* result: max chunk size dropped from 249 to a
hard-capped 200 tokens, with zero tiny fragments (previously one chunk was
just 3 tokens; now the minimum is 14).

**Page-number tracking**, which LangChain's splitter doesn't provide natively,
is preserved by concatenating all pages into one string while recording each
page's character-offset range, then recovering each output chunk's offset via
a forward-only string search (`str.find`, moving the search cursor forward
after each match) — verified against the real document to have zero lookup
failures and fully monotonic page ordering across all 210 chunks.

**Chunk size parameters** (`chunking.py`):
- `TARGET_CHUNK_TOKENS = 200`, `OVERLAP_TOKENS = 30` — sized directly against
  `all-MiniLM-L6-v2`'s own 256-token input limit, not arbitrary round numbers.
  200 leaves headroom under the ceiling; 30 tokens of overlap (~15%) keeps
  context from being lost right at a forced split boundary, without
  bloating the index with heavily duplicated content.

### 4. Vector store: ChromaDB over FAISS

FAISS is a pure nearest-neighbor math library — it knows about vectors and
array positions, nothing else. Choosing it would have meant hand-building
exactly the bookkeeping we needed anyway (a parallel id → text/metadata
lookup table, plus our own persistence for that table, since FAISS only
saves the vector index itself). Chroma stores documents, metadata, and
vectors together, keyed by our own ids, and persists all of it automatically
— `vector_store.py` is ~40 lines as a direct result.

Concretely, on disk this produces `data/processed/chroma/chroma.sqlite3` (a
real SQLite database holding text + metadata) plus a set of `.bin` files —
these are an [hnswlib](https://github.com/nmslib/hnswlib) HNSW
(Hierarchical Navigable Small World) graph index, a layered graph structure
that lets nearest-neighbor search navigate toward a query point in roughly
logarithmic time rather than comparing against every stored vector. Chroma
writes to both on every `upsert`, and loads the graph into memory to
actually execute a `.query()` — disk is the durability layer, RAM is the
working layer during search, which is the standard pattern across vector
databases generally, not something specific to Chroma.

`upsert` (rather than plain insert) also means re-ingesting the same PDF
overwrites existing chunks by id instead of duplicating them — verified by
re-running `/ingest` on the same file twice and confirming the collection
count stayed at 210, not 420.

We considered Qdrant too (more production-grade — payload filtering, built-in
hybrid search support) but it's designed around a server deployment model,
which is more infrastructure than a local single-user project needs.

### 5. Sparse search: `rank-bm25` over Whoosh/Elasticsearch

`rank-bm25` implements BM25Okapi in pure Python, in-memory, with a minimal
API. It's the standard choice in hybrid-search tutorials/projects at this
scale specifically because it keeps the focus on understanding fusion logic
rather than search-engine operations. Whoosh and Elasticsearch are more
powerful (real tokenization, stemming, phrase queries) but Elasticsearch in
particular requires running its own server process, which cuts directly
against "keep this local and simple."

**Persistence design**: `rank-bm25` has no on-disk story of its own — it's a
plain Python object that vanishes when the process exits. Rather than
building separate persistence for it (and risking it drifting out of sync
with Chroma's content), `keyword_index.py`'s `KeywordIndex.from_vector_store()`
treats **Chroma as the single source of truth** and rebuilds the BM25 index
in memory from Chroma's stored documents whenever it's needed. At this corpus
scale (~200 chunks) that rebuild is effectively free, and it eliminates an
entire category of dual-write bugs.

### 6. Fusion: Reciprocal Rank Fusion, `RRF_K = 60`

Dense and sparse scores live on completely incompatible scales — Chroma
returns a cosine *distance* (0–2, lower is better), BM25 returns an unbounded
term-frequency-based score (higher is better). You can't average them
directly. RRF sidesteps this by working off **rank position** instead of raw
score: for each result, `1 / (k + rank)`, summed across both lists it appears
in.

`RRF_K = 60` is the constant from the original paper (Cormack et al., 2009)
introducing this technique — it's large enough that rank 1 vs. rank 2 doesn't
dominate the fused score, so a chunk ranked decently by *both* methods can
beat a chunk ranked #1 by only one of them. We kept the standard value rather
than tuning it, since we had no labeled relevance data to tune against.

**`CANDIDATE_POOL = 20`**: each underlying search retrieves 20 candidates
(more than the typical final `n_results = 5`), because fusion needs a wide
enough pool from each method to find chunks that rank well *overall* even if
they weren't #1 anywhere individually.

**This is not just theoretical** — we verified it concretely on a real query
("what blood pressure threshold should start pharmacological treatment").
Two chunks appeared in *both* the dense and sparse top-5 lists; RRF correctly
promoted them to the top of the fused ranking, ahead of chunks that scored
higher in only one individual method. One chunk that was sparse search's own
#1 pick didn't make the fused top 5 at all, because it only had support from
one signal.

**A real limitation we found the hard way**: RRF only encodes rank, not
match *quality*. A query's top dense match scores identically in RRF terms
whether that match is genuinely excellent or merely "the least-bad of a bad
set." This directly caused a hallucination bug — see
[Relevance gating](#8-relevance-gating-a-bug-we-found-and-fixed) below.

### 7. Generation: Ollama + `medgemma:4b`

Chosen because it's what was already installed locally (`medgemma:4b`, a
medical-domain model), keeping the entire stack free of API keys. Calls go
through Ollama's `/api/chat` endpoint — verified against both its
non-streaming (`stream: false`, single JSON response) and streaming
(`stream: true`, newline-delimited JSON, one line per token) response shapes
before writing any code around them.

The system prompt explicitly instructs the model to answer **only** from the
provided context, cite page numbers for every claim (`(p. X)` / `(pp. X-Y)`),
say so explicitly if the context is insufficient, and includes a disclaimer
that this is not a substitute for professional medical judgment — a
deliberate choice given the corpus is clinical content, even for a demo
project.

### 8. Relevance gating — a bug we found and fixed

Asking the deployed system *"What's the WHO's position on climate change?"*
— a question entirely outside the corpus — returned a **fabricated answer
with a fabricated citation**, instead of refusing. Diagnosing it:

1. Retrieval always returns *something* — nearest-neighbor and BM25 search
   have no built-in concept of "no good match," they return the closest
   thing in the corpus regardless of how irrelevant it actually is.
2. The RRF fused score for this query looked *deceptively similar* to a
   genuinely relevant query's score (~0.03 either way) — exactly the RRF
   limitation noted above: it can't distinguish "best of great matches" from
   "best of irrelevant matches."
3. The **raw dense distance**, by contrast, separated the cases clearly:
   genuinely relevant queries measured 0.55–0.96; clearly irrelevant ones
   measured 1.45–1.84 — a real, reproducible gap, checked across six
   different queries before picking a threshold.
4. We also confirmed this wasn't simply "the prompt doesn't work" — a
   different tricky case (asking for a specific drug dosage that isn't in
   the document, but where retrieval legitimately found topically-related
   content) was already handled correctly by the prompt alone ("the context
   does not contain..."). The failure was specific to *zero-relevance*
   retrieval, where the model apparently treats the context as noise and
   falls back to its own pretrained knowledge instead of following the
   instruction to refuse.

**The fix** (`generation/llm.py`): before calling the LLM at all, check the
raw dense-search distance of the top match against `MAX_RELEVANT_DISTANCE =
1.2` (chosen from the measured gap above). If nothing sufficiently relevant
was retrieved, skip generation entirely and return a direct "not found"
message — more reliable than depending on prompt instructions alone for a
small local model, and faster, since it avoids an unnecessary LLM call.

### 9. FastAPI: streaming design

`POST /search` returns a complete JSON response (`{answer, sources}`).
`POST /search/stream` streams token-by-token for the frontend's chat UI.

The streaming response uses **newline-delimited JSON events**
(`{"type": "sources", ...}` followed by a stream of `{"type": "token", ...}`,
ending with `{"type": "done"}`), not a plain-text body with metadata in a
header. We tried the header approach first — it's simpler — but once
`sources` started carrying full chunk text (not just page numbers, per a
later request), that risked exceeding typical HTTP header size limits.
NDJSON events carry arbitrarily-sized metadata safely and is the same
general pattern most real streaming LLM APIs use.

**Path traversal protection** (`api/routes/ingest.py`): the `/ingest`
endpoint accepts a filename and resolves it against `data/raw/`, then
verifies the resolved path is still *inside* that directory
(`Path.is_relative_to`) before touching the filesystem — rejecting inputs
like `"../../../etc/passwd"`. Verified with a live request returning `400
Invalid filename` rather than silently resolving outside the intended
directory.

### 10. Frontend: Streamlit, consuming the stream lazily

`frontend/app.py` opens the streaming request manually (`client.send(...,
stream=True)`) rather than using a `with` block, specifically so it can read
the `sources` NDJSON line immediately and return a lazy generator for the
remaining token events — verified this is genuinely lazy (not buffered) by
timing it against the real backend: sources arrived in 0.2s, the first token
at ~3s (model load + prompt eval), and the full answer trickled in over
several seconds rather than arriving all at once.

## Known limitations

- **BM25 rebuild cost**: `KeywordIndex.from_vector_store()` rebuilds the
  entire BM25 index from Chroma on every call. Fine at ~200 chunks; would
  need caching (with invalidation on ingest) at larger scale.
- **Sentence splitter imperfections**: LangChain's separator cascade can
  occasionally over-split on abbreviations, but this only affects where a
  forced sub-split lands, not content loss (the hard-token-slice fallback
  guarantees no content is ever dropped).
- **RRF has no tunable relevance floor of its own** — the relevance gate in
  `generation/llm.py` compensates for this at the generation layer, but
  `fusion.search()` itself will still return its "best available" chunks for
  any query, however irrelevant.
- **Small local model (4B parameters)** is more prone to ignoring grounding
  instructions than a larger model would be — the relevance gate is a
  structural mitigation for the specific failure mode we found, not a
  guarantee against every possible prompt-following failure.
- **Single-document corpus** — path handling, ingestion, and the relevance
  threshold have only been validated against one PDF (the WHO hypertension
  guideline). A second, differently-structured document would be a good
  next stress test.

## Running it

See [Quick start](#quick-start) above for first-time setup. Day to day, once
`.env` is configured and Ollama is running:

```bash
# Backend (FastAPI)
uv run uvicorn hybrid_search_rag.api.main:app --host 127.0.0.1 --port 8000

# Frontend (Streamlit), in a second terminal
uv run streamlit run frontend/app.py
```

### Ingesting a new document

Drop a PDF into `data/raw/`, then:

```bash
curl -X POST http://127.0.0.1:8000/ingest -H "Content-Type: application/json" \
  -d '{"filename": "your_file.pdf"}'
```

## API reference

| Endpoint | Method | Purpose |
|---|---|---|
| `/health` | GET | Liveness check |
| `/search` | POST | `{question, n_results?}` → `{answer, sources}` (full response) |
| `/search/stream` | POST | Same input, streams NDJSON events (`sources`, `token`, `done`) |
| `/ingest` | POST | `{filename}` → `{source, chunks_indexed}`; ingests a PDF from `data/raw/` |
